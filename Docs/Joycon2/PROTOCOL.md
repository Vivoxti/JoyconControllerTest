# Joy-Con 2 по BLE — шпаргалка по протоколу

Конспект того, что нужно нам (кнопки, стики, LED, keep-alive). Протокол реверснут сообществом,
не официальный. Полный первоисточник и детали (IMU, вибрация, bonding, аудио):
<https://github.com/loserkidsblink/switch2mac/blob/main/research/PROTOCOL.md>
(на основе <https://github.com/ndeadly/switch2_controller_research>).
Минимальный рабочий пример на Web Bluetooth: `mascii/joy-con-2-web-bluetooth-api-demo`, `src/App.vue`.

Всё ниже — **проверить на нашем железе** (Фаза 0/1 в [PLAN.md](PLAN.md)) и при расхождении
поправить здесь.

## Обнаружение

| Что | Значение |
|---|---|
| BLE manufacturer company id | `0x0553` |
| Vendor id (внутри manufacturer data) | `0x057E` |
| PID Joy-Con 2 (R) | `0x2066` |
| PID Joy-Con 2 (L) | `0x2067` |
| PID Pro Controller 2 / NSO GameCube | `0x2069` / `0x2073` |
| Имя при рекламе | `Joy-Con 2 (L)` / `Joy-Con 2 (R)` (может быть кастомным) |

Manufacturer data (байты *после* 2-байтного company id): `[3..4]` VID LE, `[5..6]` PID LE,
`[10..15]` адрес хоста для переподключения (все нули = режим спаривания, зажат SYNC).

Фильтр Web Bluetooth (Chrome): `companyIdentifier: 0x0553`, `dataPrefix: 00 00 00 00 00 <PID LE>`,
`mask: 00 00 00 00 00 FF FF` → L: `67 20`, R: `66 20`. Bluefy фильтр по manufacturer data
не поддерживает — фильтровать по имени.

Подключаться к контроллеру можно, только пока мигают индикаторы (SYNC зажат).

## GATT

Сервис Nintendo: `ab7de9be-89fe-49ad-828f-118f09df7fd0`

| Назначение | Характеристика | Тип |
|---|---|---|
| Input report | `ab7de9be-89fe-49ad-828f-118f09df7fd2` | notify |
| Команды | `649d4ac9-8eb7-4e6c-af44-1ea54fe5f005` | write without response |
| Ответы на команды | `c765a961-d9d8-4d36-a20a-5315b111836a` | notify |
| Вибрация Joy-Con R | `fa19b0fb-cd1f-46a7-84a1-bbb09e00c149` | write without response |
| Вибрация Joy-Con L | `289326cb-a471-485d-a8f4-240c14f18241` | write without response |
| Вибрация+команды R / L (так шлёт консоль) | `65a724b3-f1e7-4a61-8078-a342376b27ff` / `ce49a830-dced-48ae-931e-c8cf88aadbea` | write without response |
| Ответы на команды #2 R / L | `640ca58e-0e88-410c-a7f3-426faf2b690b` / `63a3810f-aec7-474b-9010-3d52403cb996` | notify |
| Компактный input R / L (репорты 0x08/0x07, другой формат) | `d5a9e01e-2ffc-4cca-b20c-8b67142bf442` / `cc1bbbb5-7354-4d32-a716-a81cb241a32a` | notify |

- **Все характеристики, включая вибрацию, — в одном сервисе `…7fd0`** (ndeadly, mascii) → для Web
  Bluetooth хватит одного `optionalServices`.
- **Без SMP pairing / шифрования.** Попытка спаривания на уровне ОС — контроллер рвёт связь.
- Все записи — Write Without Response.

## Формат команды

8-байтный заголовок + payload:

```
[0] command id   [1] 0x91   [2] 0x01 (BLE)   [3] subcommand
[4] 0x00         [5] payload length          [6] 0x00   [7] 0x00
[8..] payload
```

Ответ приходит на characteristic «ответы»: `[cmd] 01 01 [sub] 10 78 00 00` (`[1]=0x01` — ответ,
`[3]` — эхо подкоманды, `[5]=0x78` — ACK), данные с `[8]`. Ответ на чтение памяти:
`[8]` длина, `[9..11]` нули, `[12..15]` адрес (LE), **данные с `[16]`**.

| Cmd/Sub | Что | Payload |
|---|---|---|
| `0x09/0x07` | Player LED | `pattern 00 00 00` (4-бит маска; P1 `0x01`, P2 `0x03`, P3 `0x07`, P4 `0x0F`) |
| `0x0C/0x02` | Задать feature mask | `flags 00 00 00` |
| `0x0C/0x04` | Включить feature mask | `flags 00 00 00` |
| `0x02/0x04` | Чтение памяти | `len 7E 00 00 addr(4 LE)`, len ≤ `0x4F` |

Feature flags: `0x01` кнопки, `0x02` стики, `0x04` IMU, `0x10` оптическая мышь (только Joy-Con 2),
`0x20` ток батареи (у ndeadly — «rumble»), `0x80` магнитометр. Консоль шлёт Joy-Con'ам **`0x37`**
(так же joycon2cpp), switch2mac — `0xB7`. **Мы используем `0x37`.**
**Не `0xFF`** — даёт фантомные ZL/ZR. (Web-демо шлёт `0xFF` — не повторять.)

Адреса памяти (чтение ≤ `0x4F` байт за раз по BLE):

| Адрес | Что |
|---|---|
| `0x00013000` | info-блок: `+0x02` серийник (16 байт ASCII), `+0x12` VID LE, **`+0x14` PID LE**, `+0x19…` цвета (ndeadly, memory_layout.md) |
| `0x000130A8` | factory-калибровка стика 1 (9 байт) |
| `0x000130E8` | factory-калибровка стика 2 (= стик 1 + `0x40`; одним чтением `0x49` байт берём оба) |
| `0x001FC040` | user-калибровка стика 1: 2 байта заголовка, данные с `0x1FC042` (`FF FF FF` = не задана) |
| `0x001FC060` | user-калибровка стика 2 (данные с `0x1FC062`) |

## Handshake

Надёжный порядок (так делает switch2mac; реализовано в `Joycon2Session`):

1. Connect (без SMP).
2. Подписка на «ответы на команды» (до любых команд).
3. (опц., мы пропускаем) Чтение info-блока — сторону L/R знаем из PID в рекламе.
4. Чтение калибровки (user `0x1FC040` → fallback factory `0x130A8`).
5. Player LED.
6. Feature mask: `0x0C/0x02`, затем `0x0C/0x04`.
7. Подписка на input report.

Каждый шаг ждёт ответа (таймаут 1 с, 2 попытки), неответивший шаг пропускается. Если подписка на
ответы не удалась — «слепой» режим: без чтения калибровки, команды с паузой 300 мс.

Минимум (так делает web-демо, и это работает): LED → mask set → mask enable → подписка на input,
с паузами между записями.

**Keep-alive:** на macOS связь молча рвётся через ~10–17 c после последней *записи* хоста.
Повторять безобидную команду (тот же LED) раз в секунду. На Windows/Linux не требуется, но делаем
везде — дёшево.

## Input report (63–64 байта, ~60+ Гц)

| Offset | Размер | Поле |
|---|---|---|
| `0x00` | 4 LE | timestamp / счётчик |
| `0x04` | 4 LE | кнопки (битовая маска ниже) |
| `0x0A` | 3 | стик 1 (упакованная пара 12 бит) — тут стик **левого** Joy-Con |
| `0x0D` | 3 | стик 2 — тут стик **правого** Joy-Con |
| `0x10`/`0x12` | 2+2 LE | оптическая мышь X/Y (абсолютные, переполнение по 2¹⁶) |
| `0x1F` | 2 LE | напряжение батареи, мВ |
| `0x30` | 6 | акселерометр X/Y/Z (3× int16 LE) |
| `0x36` | 6 | гироскоп X/Y/Z (3× int16 LE) |

Стик: 3 байта → 24-бит LE; младшие 12 бит = X, старшие 12 = Y, диапазон 0–4095
(`x = b0 | (b1 & 0x0F) << 8; y = b1 >> 4 | b2 << 4`). Неиспользуемое поле стика у Joy-Con = `0x7FF`.
Report ID в BLE-репорте нет; L и R шлют одинаковый формат. Байт `0x29` всегда `0x01`.

**Квирк правого Joy-Con:** стик приходит во *втором* поле (`0x0D`), а калибровка у него — в слоте
*стика 1*. Калибровать правый стик калибровкой стика 2 → мёртвая ось.

Калибровка (9 байт): центр, max, min — по упакованной паре 12 бит; **max и min — это размах
относительно центра**, а не абсолютные значения. `v = raw − center`; положительная сторона делится на
`max`, отрицательная на `min`; clamp ±1. Пример (ndeadly): `B3 67 83 2E 66 5E 3A 06 5F` → центр
(1971, 2102), +(1582, 1510), −(1594, 1520). Без калибровки берём центр 2048 и размах ±1250.

### Кнопки (`0x04`, uint32 LE)

| Бит | Кнопка | Бит | Кнопка | Бит | Кнопка |
|---|---|---|---|---|---|
| `0x00000001` | Y | `0x00000100` | Minus | `0x00010000` | D-Down |
| `0x00000002` | X | `0x00000200` | Plus | `0x00020000` | D-Up |
| `0x00000004` | B | `0x00000400` | R-stick | `0x00040000` | D-Right |
| `0x00000008` | A | `0x00000800` | L-stick | `0x00080000` | D-Left |
| `0x00000010` | SR (R) | `0x00001000` | Home | `0x00100000` | SR (L) |
| `0x00000020` | SL (R) | `0x00002000` | Capture | `0x00200000` | SL (L) |
| `0x00000040` | R | `0x00004000` | C | `0x00400000` | L |
| `0x00000080` | ZR | | | `0x00800000` | ZL |

### IMU (`0x30` акселерометр, `0x36` гироскоп, 3× int16 LE)

- Включается битом `0x04` feature mask (наш `0x37` его содержит), других команд не нужно. Пока IMU
  выключен, байты нулевые; валидный сэмпл — когда `[0x29] == 0x01` и акселерометр не нулевой.
- Масштаб: акселерометр **4096 LSB = 1 g** (±8 g; ndeadly, switch2mac, joycon2cpp согласны).
  Гироскоп **±2000 °/с → 2000/32767 °/с на LSB** (ndeadly, по даташиту ICM-42670-P; switch2mac
  согласен). joycon2cpp использует масштаб в ~8 раз меньше — **проверить**: повернуть на 360° и
  проинтегрировать.
- Один сэмпл на репорт → частота IMU = частоте репортов. `[0x2A]` — u32 timestamp в мкс (не у всех
  контроллеров корректен), `[0x2E]` — температура, 25 + raw/127 °C.
- Калибровка: в `0x1FC000` (0x40) лежит user motion calibration (формат не описан), на factory-блоки
  `0x13040` / `0x13100` есть только догадки. Ни один проект её не читает → **оцениваем дрейф гироскопа
  в покое сами** (`Joycon2GyroBias`).
- **Ориентация осей не задокументирована нигде** и ни один проект оси не переставляет. Единственная
  зацепка (switch2mac): лёжа лицом вверх, +Z ≈ +1 g, X и Y — в плоскости лицевой панели.
  Принятая система (`Joycon2MotionAxes`): правая тройка; Joy-Con вертикально, лицом к себе:
  **+Y — к торцу с L/R, +X — к правому краю, +Z — из лицевой панели.** Первая догадка (+X к торцу)
  давала поворот всех наклонов на 90° — исправлено по проверке на железе 2026-10-13 (один Joy-Con;
  вторая сторона — по симметрии, подтвердить). **Проверка на железе** — оверлей F9,
  строки `gyro` / `accel` (система координат «боком»):

  | Действие (Joy-Con боком, рейка SL/SR от себя) | Ожидаем |
  |---|---|
  | Лежит лицом вверх | `accel up ≈ +1` |
  | Поднять правый торец | `accel right > 0` |
  | Наклонить рейку от себя вниз | `accel fwd < 0`, во время движения `pitch > 0` |
  | Повернуть вправо, как стрелку на столе | `turn > 0` |
  | Крутить как руль вправо (правый торец вниз) | `roll < 0` |

  Если знак/ось не совпали — поправить таблицу в `Joycon2MotionAxes` (одна таблица на сторону;
  гироскоп и акселерометр берут её оба).

## Платформенные заметки

- **Windows:** не спаривать через «Параметры». Если Joy-Con когда-то спаривали — удалить его из
  «Bluetooth и устройства» (иначе кэш GATT/имени мешает). WinRT: `GattSession.MaintainConnection = true`,
  discovery с `BluetoothCacheMode.Uncached` и ретраями. **Частота репортов:** контроллер сам не просит
  смену connection interval → на Windows 10 интервал 60 мс ≈ **16,7 Гц** (ndeadly); на Windows 11
  `BluetoothLEDevice.RequestPreferredConnectionParameters(ThroughputOptimized)` (так делает joycon2cpp;
  мы тоже). Частые повторные коннекты подряд → контроллер «глохнет» на несколько минут: нужен back-off.
- **macOS:** keep-alive 1 Гц; потолок ~66 Гц (connection interval не управляется).
  `NSBluetoothAlwaysUsageDescription`.
- **Android:** `requestMtu(517)` до подписки (иначе нотификации режутся до 20 байт); GATT-операции
  строго по одной.
- **Web:** HTTPS/localhost, `requestDevice` только из жеста пользователя, один chooser = одно
  устройство, reload рвёт соединение. Manufacturer data странице не отдаётся, а имя Chrome может не знать
  («Unknown or unsupported device», проверено на Windows) → сторону L/R читаем из info-блока (`0x13014`).
